# 短信推送助手 / SmsForwarder Assistant · Bark-Android v1.3.4

[中文使用说明](https://github.com/1Fann/SmsForwarder-assistant/blob/v1.3.4/README.md) · [English guide](https://github.com/1Fann/SmsForwarder-assistant/blob/v1.3.4/README.en.md)

## 中文

**安卓 Bark 服务端与短信推送助手。** 本次为源码发布，不附带 APK 安装包。下方自动生成的 Source code ZIP / tar.gz 是源码，不能直接安装到手机。

### 两种用途

- **独立安卓 Bark 服务端**：在 ARM64 安卓手机上启动 Bark、查看配对地址、绑定 iPhone 并发送测试提醒。只需要自建 Bark 服务的人也能使用，无需安装或启用短信转发器。
- **安卓短信推送到 iPhone**：配合官方 SmsForwarder 完成初始配置，并可在第 4 步启用助手自有的可靠短信投递模式。

### v1.3.4 功能

保留 Android 适配的 Bark 服务端 2.3.9、手动启停、权限修复及独立 Root 守护。完整检查间隔 1–1440 分钟，默认 5 分钟；已知进程存活状态约每秒检查。

新增可靠短信投递模式。在首次配置页完成第 4 步后，助手从本次启用的系统短信编号开始，每 5 秒核对收件箱，并将新短信写入本机持久队列。队列成功保存后才推进同步位置；应用或服务重启会继续处理，同一短信编号不会再次入队。启用前的历史短信不会批量推送。

接管仅停用本助手创建、指向本机随机访问路径的“全部短信转发至 iPhone”规则，其它用户规则保留。已修改为单 SIM、静默时段或自定义模板/加密的助手规则会拒绝自动接管，需要先核对设置。原短信转发器无需更换签名。更新 APK 本身不会自动切换转发方式。切换前会持久保存同步起点，失败重试不会跳过中间收到的短信。

Bark 接收通知后先保存到本机队列再确认接收。网络或 APNs 失败会持续重试，间隔从 5 秒增加至最多 5 分钟。首页显示待投递和重试数量。本机接收成功表示已保存，并不等同于 iPhone 已收到。外部接受请求后、记录成功前进程退出仍可能产生重复，不能保证严格的一次投递。切换时原转发器的在途请求也可能重复。

更新守护脚本时先完整准备新文件，保留期望启用状态；普通失败恢复旧文件，开机入口处理未完成的更新记录。后台服务不会因中途复制失败而被永久关闭。

首页还显示损坏记录数量；损坏队列记录保留隔离，正常记录继续处理。确认重新对账当前收件箱可能重推现有短信。

### 使用与构建

- Android 8.0+、ARM64、iPhone Bark。短信自动配置、可靠模式接管、权限修复及独立定时守护需要 Root；可靠模式还需要 READ_SMS 权限。
- 在首次配置页完成第 4 步，才会启用可靠短信对账。安装更新本身不会自动切换转发方式，原短信转发器无需更换签名。单独启动 Bark 不调用 Root，但非 Root 设备尚未实机验证；已验证环境为 Android 13 / 红米 Note 10 Pro / MIUI 14 / Magisk。
- 首次配对使用同一 Wi-Fi；配对后 iPhone 通过 Apple APNs 收通知，日常接收不要求与安卓在同一 Wi-Fi。访问 Bark 接口的调用方仍须能连接安卓服务。
- 源码构建时，准备脚本从官方获取依赖并校验固定 SHA-256；获取的推送组件及官方短信转发器会打包进本地生成的 APK。
- 构建步骤和操作流程见[中文使用说明](https://github.com/1Fann/SmsForwarder-assistant/blob/v1.3.4/README.md)。本次 Release 不执行 APK 构建或上传。

本版本 APK 仅用于本地已授权部署。现有上游 APNs 私钥仍在引擎内，不能公开发布该二进制；源码发布必须继续排除该私钥文件。

### 验证范围

本地验证覆盖队列重启续投、超过五次失败、系统时间回调、相同文本的不同短信、系统短信编号去重、存储不可用拒绝确认、HTTP 入口、更新失败回滚和中断恢复。未发送真实短信或通知。可靠模式需要 READ_SMS 权限；短信在首次扫描前被用户删除、系统短信编号回退会锁存提示，需确认重新对账当前收件箱并生成新的身份空间；磁盘耗尽和 APNs 永久拒绝仍需处理。队列最多保存 10,000 条待投递通知，满时拒绝接收且不推进系统短信游标。

2026-11-01 实机确认：原签名 1.3.4 已覆盖安装，三份守护脚本与 APK 一致。可靠短信接管成功，READ_SMS 已授予，待投递、重试和损坏记录数均为 0。守护进程退出后一次观测恢复为 0.61 秒。黑屏、插电时，Bark 业务进程退出至本机 HTTP 与前台就绪为 1.64 秒；旧短信转发器退出至前台和权限就绪为 3.22 秒，随后均稳定观察 3 秒。这些单次样本不构成上限保证，3.22 秒也不属于严格 3 秒内。整机重启验证已完成，从重启请求起计、包含系统启动：系统完成 37.53 秒，Bark 本机 ping 就绪 44.39 秒，短信转发器前台和权限就绪 44.83 秒，全套就绪 62.06 秒、稳定确认 66.08 秒。该红米 `deviceSecure=false`，观察者未人工解锁、未启动界面或服务。仅验证本机就绪，未主动发送真实短信或通知，未验证 APNs 实际到达；结果不代表带安全锁屏凭据设备可免首次解锁。详见 [验证记录](https://github.com/1Fann/SmsForwarder-assistant/blob/v1.3.4/docs/RELIABILITY.md)。

## English

**A Bark server for Android, with optional SMS forwarding to iPhone.** This is a source-only release with no APK attached. The automatically generated Source code ZIP / tar.gz archives contain source code and cannot be installed directly on a phone.

### Two use cases

- **Standalone Bark server on Android**: start Bark on an ARM64 Android phone, view registration addresses, register an iPhone, and send test notifications. You can use it solely to host Bark without installing or enabling SmsForwarder.
- **Android SMS notifications on iPhone**: complete initial configuration with the official SmsForwarder app, then optionally enable the assistant's reliable SMS delivery mode in setup step 4.

### v1.3.4 features

Retains Bark server 2.3.9 adapted for Android, manual start/stop controls, permission repairs, and independent root monitoring. Full checks run every 1–1440 minutes, defaulting to 5 minutes; known-process liveness is checked approximately every second.

Reliable SMS delivery is an explicit opt-in in setup step 4. The assistant captures the current system SMS ID as its starting point, reconciles the inbox every five seconds, and advances its cursor only after the local durable queue acknowledges storage. Application and engine restarts resume pending work. Persistent IDs prevent replay of the same provider row while allowing identical text in distinct messages. Older messages are not replayed when first enabled.

Takeover disables only the assistant-created all-SMS rule pointing to its own local namespace. Customized SIM filters, quiet periods, templates and encryption are rejected for automatic takeover and require review. Other user rules remain intact, and the third-party forwarder's signing identity is unchanged. Installing the APK does not switch delivery modes automatically. The migration boundary is persisted before pausing the old sender and retained when migration is retried.

The Android Bark engine persists incoming notifications before acknowledging acceptance, then retries network and APNs failures with a five-second to five-minute backoff. The app shows pending and retrying counts. Acceptance means durable local storage, not confirmed iPhone receipt. A crash after remote acceptance but before local completion can still duplicate a notification; old in-flight requests can also duplicate during migration.

Monitor updates prepare complete files before retiring existing workers, preserve desired state, roll back ordinary failures, and recover unfinished transactions at boot.

The app also reports damaged-record counts. Damaged queue records are retained in quarantine while healthy records continue. Explicitly reconciling the current inbox may repeat existing messages.

### Usage and building

- Requires Android 8.0+, ARM64, and Bark on iPhone. SMS configuration, reliable-mode takeover, permission repairs, and independent monitoring require root. Reliable mode also requires READ_SMS.
- Enable reliable reconciliation explicitly in setup step 4. Installing the APK does not switch delivery modes automatically, and the third-party forwarder's signing identity is unchanged. Standalone Bark startup does not invoke root, but unrooted operation has not been tested on hardware. The verified environment is Android 13 / Redmi Note 10 Pro / MIUI 14 / Magisk.
- Initial registration uses the same Wi-Fi. The iPhone subsequently receives notifications through Apple APNs and need not remain on that Wi-Fi. Applications calling the Bark endpoint must still be able to reach the Android server.
- At build time, the preparation script obtains official upstream dependencies and verifies pinned SHA-256 hashes. The push component and official SmsForwarder installer are bundled into the locally built APK.
- See the [English guide](https://github.com/1Fann/SmsForwarder-assistant/blob/v1.3.4/README.en.md) for build steps and operation details. This release does not build or upload an APK. The app's interface is Chinese; the English guide translates the relevant controls.

The APK is for authorized local deployment only. The engine still contains the upstream APNs private key and must not be publicly uploaded. Source publication must continue excluding that key file.

### Validation and licensing

Offline tests cover queue restart, extended retries, clock rollback, provider-ID deduplication, storage failures, the HTTP ingress, updater rollback and interrupted transactions. No real notification or SMS was sent. READ_SMS is required. Deleted-before-scan messages, provider ID rollback (which latches a warning until an explicit inbox reconciliation starts a new identity generation), full storage and permanent APNs rejection remain visible limitations. A full 10,000-message queue rejects new acceptance without advancing the SMS cursor.

Device checkpoint on 2026-11-01: the production-signed 1.3.4 update was installed and all three deployed monitor scripts matched the APK. Reliable SMS takeover succeeded, READ_SMS was granted, and pending, retrying, and blocked counts were zero. One checker-exit test observed recovery after 0.61 seconds. With the phone plugged in and screen-off, Bark process exit to local HTTP and foreground readiness took 1.64 seconds; existing SmsForwarder process exit to foreground and permission readiness took 3.22 seconds, followed by three seconds of stable observation in each case. These individual samples are not guaranteed upper bounds, and 3.22 seconds is not strictly within three seconds. No real SMS or notification was deliberately sent and actual APNs arrival was not verified. Full-device reboot validation completed. Measured from the reboot request and including system startup, boot completion took 37.53 seconds, Bark local ping readiness 44.39 seconds, SmsForwarder foreground and permission readiness 44.83 seconds, all-service readiness 62.06 seconds, and stable confirmation 66.08 seconds. The Redmi reported `deviceSecure=false`; the observer issued no unlock, Activity-launch, or service-start commands. This validates local readiness and does not establish pre-first-unlock behavior on a phone with secure lock-screen credentials. See the [validation record](https://github.com/1Fann/SmsForwarder-assistant/blob/v1.3.4/docs/RELIABILITY.md).

A complete first install on a second, fresh phone remains untested.
